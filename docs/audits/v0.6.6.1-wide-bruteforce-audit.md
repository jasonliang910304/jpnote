# 3. 高優先修正

## H1. Pending relation 可以無聲覆蓋較新的 relation note

### Import 路徑

既有 DB：

```text
A → B｜意思相近｜OLD_PENDING
```

因為 B 尚未存在，所以它在 `pending_grammar_relations`。

之後匯入 B，同一批資料明確提供：

```text
B → A｜意思相近｜NEW_INCOMING
```

v0.6.6.1 preflight 顯示：

```text
B → A = new
conflict = 0
```

實際 apply 的最終資料卻變成：

```text
A → B｜OLD_PENDING
B → A｜OLD_PENDING
```

也就是舊 pending note 在 `resolve_pending_relations()` 階段把本次新資料覆蓋掉，而且沒有 conflict。

### Repair 路徑

若 DB 已存在：

```text
A ↔ B｜NEW
```

另外又殘留：

```text
pending A → B｜OLD
```

`jpnote audit` 只把 pending row 標成 `fixable`。

執行：

```bash
jpnote repair --yes
```

會把既有 `NEW` 無聲改成 `OLD`，並回報無 unresolved。

### 建議

- pending → resolved 前先和既有 logical relation + reciprocal/inverse 比較。
- 不同非空 note → `conflict/review`，不能自動 resolve。
- preflight 必須模擬既有 pending relations 在本次新增 target 後的 resolution。
- repair 對此類狀態只能列 unresolved，不得 last-write-wins。

**優先度：Critical/High。**

## H2. Attempt identity 已做格式正規化，但 content comparison 沒有，造成假 conflict

例如第一次匯入：

```text
section = 第１課
question = 問題 1
```

第二次完全同一筆內容，只改成：

```text
section = 第1課
question = 問題1
```

identity normalization 會把它們視為同一筆，因此 generated `event_key` 相同。

但 `attempt_content_signature()` 比較的是未做同等正規化的 raw fields，因此 preflight 會變成：

```text
status = conflict
```

真正 import 也會拒絕。

這和 v0.6.4 之後「`問題3` / `問題 3` / `問題３` 是同一 locator」的契約不一致。

同類問題也可能出現在 prompt / user_answer 的 harmless NFKC 或 whitespace differences。

### 建議

content signature 至少對 identity 定義為 harmless 的欄位使用相同 normalization，再比較 enrichment/correction fields。

**優先度：High。**

---

## H3. Manual `edit` 沒有 unknown-field protection，拼字錯誤可直接清空資料

Import JSON 已經會拒絕：

```json
{"readng": "ねこ"}
```

但是 `jpnote edit` 的臨時 JSON 沒有套用相同的 unknown-field boundary。

實測把：

```json
"reading": "ねこ"
```

誤改成：

```json
"readng": "ねこ"
```

程式接受並完成更新，最終：

```text
reading = ""
```

同樣地，`jpnote attempts edit` 把：

```text
correct_answer → correct_answr
```

後，正確答案被清成空字串。

### 建議

- Entry edit 定義自己的 allowed-edit-fields（需包含 `sources`）。
- Attempt edit 使用 public attempt fields 的 strict unknown check。
- 在實際 replace 前拒絕任何未知欄位。

**優先度：High，屬於資料安全問題。**

## H4. Malformed nested JSON type 可以繞過預期 ValueError，直接產生 Python traceback

5,000 組 malformed payload fuzz 找到多個未捕捉 `TypeError`。

最小例：

```json
{
  "items": [
    {
      "key": "vocab:X",
      "type": "vocabulary",
      "display": "X",
      "senses": 1.2
    }
  ]
}
```

執行 `--check` 不是得到：

```text
senses 必須是陣列
```

而是完整 traceback：

```text
TypeError: 'float' object is not iterable
```

根因在 `_validate_public_payload_fields()` 先直接 iteration nested fields，早於正式 type validator。

同類：

- `related_grammar: 1`
- `parts: 1`
- `options: true`

都可能走到同一類 traceback。

### 建議

unknown-field walker 只有在 nested value 已確認為 list 時才走訪元素；型別錯誤交由 normalize/validate function 回報精準 ValueError。

**優先度：High robustness。**

## H5. Audit 能偵測損壞 structured attempt，但 presentation/export/repair 可能直接 crash

人工注入：

```text
question_type = reorder_4
parts_json = ["oops"]
```

`jpnote audit` 可以安全回報：

```text
invalid_reorder_parts
```

但下列操作會出現未捕捉 traceback：

```bash
jpnote attempts show attempt:bad
jpnote mistakes
jpnote export
jpnote repair --yes
```

典型錯誤：

```text
TypeError: string indices must be integers, not 'str'
```

尤其 `repair --yes` 會因最後 `export_all()` crash 而整批 rollback，因此只要有一筆這類 legacy/corrupt attempt，就可能阻擋其他原本能安全修復的資料。

### 建議

- Presentation/export 對已損壞 options/parts/order 採 fail-soft rendering。
- 顯示 `[資料格式損壞，請先 audit]`，不要直接 index dict。
- repair 應能完成其他 deterministic repair，再把這筆列 unresolved。

**優先度：High robustness / recovery。**

---

## H6. No-op mutation 仍會發布 undo backup，可能把真正有用的 rollback point 擠掉

完全相同的 payload 重複 import 5 次：

```text
DB data = unchanged
backup count = +5
```

更嚴重的模擬：DB 約 30 MiB，而 undo cap = 50 MiB。

1. 真正新增 A → 建立 backup #1（backup 內容沒有 A）
2. 對完全相同資料再做一次 no-op import
3. 建立 backup #2（backup 內容已有 A）
4. 因 50 MiB cap，#1 被 prune

最後只剩：

```text
backup #2：A 已存在
```

原本唯一能撤銷「新增 A」的 backup 已消失。

同類風險可能出現在 no-op edit / clean repair 等 mutation wrappers。

### 建議

pending snapshot 只有在 transaction 實際改變資料後才 publish；真正 no-op 時直接刪除 pending snapshot。

**優先度：High data-safety，尤其 DB 成長後。**

---

## H7. Legacy relation label 狀態下，preflight 與真正 apply 再次分歧

DB 殘留：

```text
A ↔ B｜相反／對比｜same
```

匯入 canonical：

```text
A → B｜對比｜same
```

`connect_preflight()` 會在記憶體 snapshot 先 normalize legacy relation value，因此 preflight 顯示：

```text
relation = unchanged
item = unchanged
```

但正式 `connect()` 現在故意不會自動 normalize legacy relation，以便 audit 看得到歷史問題。

實際 apply 結果：

```text
舊 相反／對比 rows 仍在
新 對比 rows 又新增
```

apply 回報 item updated / added relations。

### 建議

preflight 與 apply 必須使用同一種 legacy-data visibility。不要在 preflight snapshot 偷做 apply 不會做的 data-value repair；或把這種 normalization 明確納入 apply plan。

**優先度：High preflight correctness，但已跑過 v0.6.6 repair 的乾淨 DB 不易觸發。**

# 4. 中優先修正

## M1. Preflight 沒有呈現「新增 target 會自動 resolve 既有 pending relation」的副作用

既有：

```text
A → B pending
```

本次只匯入 B。

Preflight：

```text
new item = B
new/update relation = 0
```

Apply：

```text
resolved_relations = 1
DB 最終多出 A ↔ B resolved rows
A.updated_at 也可能改變
```

即使 note 沒衝突，`--check` 也沒有把完整 side effect 呈現出來。

這可和 H1 一起修。

---

## M2. Self relation 被接受；preflight 說 new，但 apply 靜默忽略

輸入：

```text
A → A｜意思相近
```

Preflight：

```text
new_relations = 1
```

Apply：

```text
added_relations = 0
```

DB 沒 relation，也沒有 error。

建議 public validation 直接拒絕 self relation，或至少 preflight/apply 都一致標為 invalid/unchanged。

---

## M3. 編輯一個 relation note，會重建該 entry 所有 relation，導致 provenance 被重置

原本：

```text
source = book-A
created_at = 原時間
```

只修改 A→B 的 note 後，A 相關的其他完全沒改 relation 也被重建成：

```text
source = manual edit
created_at = 現在
```

內容關聯仍正確，但 relation 的來源與建立時間歷史被破壞。

建議改成 logical relation diff/upsert，不要 delete-all/recreate-all。

---

## M4. `updated_at` 只有秒級精度，快速更新可能仍等於 `created_at`

直接連續 create → update：

```text
created_at = 2026-...:50
updated_at = 2026-...:50
```

`jpnote recent` 以：

```python
created_at == updated_at
```

判定 added/updated，因此這筆實際已更新的資料仍會顯示 `added`。

建議 timestamp 改 microseconds，或不要用 timestamp equality 推導 action。

---

## M5. SIGKILL 可留下 `.pending-*` backup，之後一般命令不會清理

在 `mutation_backup()` 建立 hidden pending snapshot 後直接 `kill -9`：

```text
.pending-...-killtest.db
```

會永久留在 backup dir。

之後跑 `stats` 仍不會清理，而且 `.pending-*` 不計入 active backup 50 MiB cap。

DB transaction 本身經測試可以正常 rollback、`quick_check=ok`；問題主要是 orphan pending backup 會累積與繞過容量限制。

建議啟動時清理明顯過期 `.pending-*`，或在 backup maintenance 中納入 orphan recovery policy。

---

## M6. Concurrent writers 仍會直接 `database is locked`

20 個程序同時匯入不同 entry：

```text
18 success
2 database is locked
```

最終 SQLite `quick_check` / FK 沒有 corruption，也沒有觀察到半筆資料。

單人 CLI 尚可接受；但 GUI/Web/PWA 或背景任務之前仍需要：

- busy timeout / retry policy
- writer serialization / process lock

這和原本 Web 前 writer-policy TODO 一致。

---

## M7. 最新 undo backup 損壞時，無法選擇較舊有效 backup

若最新 `undo-*.db` 損壞：

```bash
jpnote undo
```

會正確拒絕 restore，但不會 fallback / 提供選擇較舊 backup。

而且在驗證最新 backup 前就先建立一份 `recovery-before-undo` snapshot，因此失敗的 undo 也會新增 recovery file。

既有有效舊 backup 仍保留，沒有資料損壞。

建議未來提供：

```text
jpnote undo --list / --backup NAME
```

或自動跳過 corrupt newest 並要求確認下一個。

# 5. 低優先／可延後

## L1. `--item-key` / `--attempt-index` 輸入不存在值時靜默變成 no-selection

例如：

```bash
jpnote import data.json --check --item-key vocab:不存在
jpnote import data.json --attempt-index 99
```

都 exit 0；前者得到空 preflight，後者得到：

```json
{"result":"no_selection","modified":false}
```

沒有提示 selector 寫錯。

建議 explicit selector 若沒有 match 就 error；`attempt-index` 也應拒絕負值/out-of-range。

---

## L2. Auto attempt identity matching仍是線性掃描

Benchmark：

```text
5000 existing attempts × 100 classify ≈ 7.69 s
2000 existing attempts + apply 100 generated attempts ≈ 6.03 s
```

目前資料量不大時影響有限，但大量歷史/Quiz data 之後應避免每筆重掃整張 attempts。

注意：未來 Quiz history 已傾向使用獨立 study/quiz history，因此不一定要靠 attempts schema 解決。

# 7. 建議下一步

不建議直接從 v0.6.6.1 進 Review/Quiz。

建議先做一個 correctness/recovery patch（版本號可之後再決定），優先順序：

1. pending relation conflict-safe resolution + preflight simulation
2. attempt content normalization 與 identity normalization 對齊
3. manual edit strict unknown fields
4. malformed nested JSON 不得 traceback
5. malformed attempt presentation/export fail-soft
6. no-op mutation 不發布 backup
7. legacy relation preflight/apply visibility 對齊
8. self relation validation
9. relation edit provenance preservation
10. pending backup crash cleanup
11. timestamp precision / recent action
12. selector typo diagnostics

修完 1–8 後，至少再做一次：

```text
pending × import × repair
attempt identity × formatting
edit × typo fuzz
corrupt structured attempt × audit/repair/export
backup × no-op × cap
```

集中 regression，再開始 Review Queue 會比較安全。
