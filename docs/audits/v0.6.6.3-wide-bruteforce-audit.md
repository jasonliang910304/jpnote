# jpnote v0.6.6.3 廣域暴力健檢報告

日期：2026-07-24（Asia/Taipei）

> 本報告針對 `jpnote v0.6.6.3` Git 基準與使用者提供的真實 `jpnote.db` 副本進行測試。
> 所有破壞性測試均使用隔離資料庫；未修改使用者提供的原始資料庫快照。

## 1. 結論摘要

v0.6.6.3 的一般 CLI、匯入 preflight、relation merge、attempt identity、transaction rollback、migration 與真實資料庫完整性表現良好；目前沒有發現正常單人 CLI 操作會直接造成 SQLite corruption 的路徑。

然而，這輪找到兩項在進入長時間執行的 Quiz TUI 前必須修正的 blocker：

1. **文法 relation 編輯會無聲刪除該項目的 pending relations。**
2. **部分 raw SQLite helper 沒有顯式關閉 connection，長駐程序會持續累積檔案描述符。**

此外，public `JpnoteCore` 的寫入 API 尚未經過與 CLI 相同的安全 mutation pipeline。這在未來 Quiz／TUI／Web 開始透過 public core 寫資料前必須收斂成共用服務。

建議先做集中 maintenance patch，再跑 targeted regression；修正 blocker 後即可建立 stability gate，不再重複無限期廣域健檢。

## 4. 新發現：必修 blocker

## H1. Relation edit 會無聲刪除 pending relations

### 重現

既有狀態：

```text
A → B    resolved
A → M    pending（M 尚不存在）
```

只編輯 `A → B` 的 note 後：

```text
A → B    更新成功
A → M    pending row 消失
```

### 根因

`replace_entry_data()` 在 relation signature 改變時會執行：

```text
DELETE FROM grammar_relations
DELETE FROM pending_grammar_relations
```

範圍包含所有 source/target 為該 entry 的 rows；但 manual editor 只序列化 `related_grammar`，沒有帶回 `pending_related_grammar`，因此 pending relations 無法重建。

### 風險

這是無提示的資料遺失。只要文法同時存在 resolved 與 pending relation，修改一條已解析 relation 就可能刪除尚未補齊的關聯。

### 建議修正

- relation edit 改為 logical diff/upsert。
- resolved 與 pending relations 分別保存。
- 只刪除使用者明確移除的 logical relation。
- 補 regression：resolved edit 不得改動 unrelated resolved／pending rows。

**優先度：Critical/High；Quiz 前必修。**

## H2. Raw SQLite helper connection leak

### 受影響位置

`jpnote_app/db.py` 中至少包括：

- `_sqlite_integrity_ok()`
- `_create_sqlite_snapshot()`
- `restore_database_from()`
- `connect_preflight()` 的 source connection

這些程式使用：

```python
with sqlite3.connect(...) as conn:
```

Python 的 sqlite3 connection context manager只處理 commit/rollback，不保證在離開區塊時關閉 connection。

### 實測

關閉 GC 後：

```text
起始 open FDs                    4
300 次 connect_preflight       304
再做 100 次 integrity check    404
強制 GC 後                       4
```

備份與 restore 路徑也會累積 connection，直到 GC 回收。

以 development mode + ResourceWarning as error 執行測試時，出現與未關閉 sqlite connection 相關的失敗。

### 風險

短命 CLI 通常在 process 結束時釋放，因此日常不容易察覺；但 Quiz TUI、Web service 或背景程序會長期存活，可能耗盡 file descriptors 或保留不必要的 SQLite resources。

### 建議修正

使用其中一種方式：

```python
from contextlib import closing
with closing(sqlite3.connect(...)) as conn:
    ...
```

或明確 `try/finally: conn.close()`。

補測試時應暫停 GC，重複呼叫 helper 並確認 FD 數不隨次數線性增長。

**優先度：High；長駐 TUI 前必修。**

## H3. Public core mutation methods 繞過 CLI 安全 pipeline

### 現況

`JpnoteCore` 的多個 mutation methods 直接開啟 writable connection 並呼叫底層 service，例如：

- `apply_import()`
- `normalize_romaji()`
- `update_attempt()`
- `delete_attempt()`
- `repair()`
- `merge()`

### 實測

- `JpnoteCore.apply_import()` 寫入成功，但沒有建立 undo backup，也沒有刷新 export。
- 對已有相同 display 的資料再次從 API 匯入，可繞過 CLI 會要求處理的 duplicate warning／confirmation。

### 風險

目前 CLI 路徑安全，但未來 TUI／Web／plugin 若直接使用 public core mutation，就可能沒有：

```text
validation
→ preflight
→ duplicate/conflict gate
→ backup
→ transaction
→ export
→ structured result
```

### 建議修正

建立唯一的 `SafeMutationService`／public mutation facade；CLI、TUI、Web 與 plugin 都只能透過它寫入。

Quiz v1 若只透過 read-only core services 取題，並用獨立 Quiz history store 寫入，可先隔離；但任何 core data mutation 不得使用現有 unsafe public methods。

**優先度：High architecture；Quiz 寫入整合前必修。**

## 5. 已知、仍可重現的 recovery／correctness backlog

## M1. Relation edit 會洗掉 provenance

只修改一條 A→B relation note，與 A 相連但內容未改的其他 relations 也會被 delete/recreate：

```text
source       book-A → manual edit
created_at   可能重設
```

應與 H1 一起改成 logical diff/upsert。

**優先度：High/Medium。**

## M2. 秒級 timestamp 讓 `recent` 誤判

同一秒 create→update：

```text
created_at == updated_at
```

`recent` 依兩者相等判斷 added／updated，因此實際更新仍可能顯示為 added。

建議使用 microseconds，或不要用 timestamp equality 推導 action。

**優先度：Medium。**

## M3. SIGKILL orphan pending backup／commit-publish gap

若在 pending snapshot 建立後 `kill -9`：

- `.pending-*.db` 會留下。
- 一般啟動不會清理或回收。
- 不列入 active backup 50 MiB cap。

更嚴重的時序：DB transaction 已 commit、但 pending snapshot 尚未 publish 時被 kill：

- mutation 已保留。
- active undo backup 不存在。
- 唯一 pre-mutation snapshot 只剩 hidden `.pending-*`。

建議啟動時辨識 orphan pending snapshot，依 integrity、時間與 DB 狀態提供安全 promotion/recovery policy。

**優先度：High recovery。**

## M4. 最新 undo 損壞時不能選較舊有效 backup

目前會安全拒絕 corrupt newest，但：

- 無法列出／指定較舊 backup。
- 驗證失敗前會先建立新的 `recovery-before-undo` snapshot。

建議：

```text
jpnote undo --list
jpnote undo --backup NAME
```

流程改為先驗證目標，再建立 recovery snapshot。

**優先度：Medium。**

## M5. Recovery／restored backup 未納入容量上限

多次 undo 後，會累積：

```text
recovery-*.db
backups/restored/undo-*.db
```

目前 50 MiB cap 只管理 active `undo-*.db`，上述檔案可無限成長。

建議為 recovery/restored 設獨立保留數量或總容量政策。

**優先度：Medium storage。**

## M6. Explicit selector 拼錯仍靜默成功

```text
--item-key vocab:不存在       exit 0，空 preflight
--attempt-index 99            exit 0，no_selection
--attempt-index -1            exit 0，no_selection
```

明確指定 selector 時應回報 input error；只有互動模式取消才是正常 no-selection。

**優先度：Low。**

## M7. Concurrent writers 仍可能 `database is locked`

40 個程序同時匯入不同 entry：

```text
33 success
7 database is locked
```

最終：

```text
quick_check = ok
foreign_key_check = 0
無半筆資料
```

單人 CLI 不阻塞 Quiz；未來多 writer／background job 前需 busy timeout、有限 retry 與 writer serialization。

**優先度：P3；Web/GUI/background writer 前必修。**

## M8. Attempt identity matching 大量資料下仍偏慢

```text
5000 existing attempts × 100 classifications ≈ 9.98 秒
```

目前資料量尚可接受。Quiz history 已規劃獨立 schema，因此不應直接擴大既有 attempts 線性掃描問題。

**優先度：P2 performance。**

## 8. Stability gate 判定

### 目前判定：尚未通過

阻塞原因：

1. relation edit 可無聲刪除 pending relations。
2. raw SQLite helper connection leak 不適合長駐 TUI。
3. public mutation API 尚未收斂到共用安全 pipeline。

### 建議 maintenance patch 範圍

P0/P1：

1. relation edit logical diff/upsert，保留 pending 與 provenance。
2. 顯式關閉所有 raw SQLite connections，加入 FD leak regression。
3. 建立／收斂 Safe Mutation Service；至少封鎖 unsafe public mutations 被 TUI 使用。
4. SIGKILL orphan pending backup recovery policy。

可同版處理：

5. timestamp precision/recent action。
6. undo list／指定 backup／先驗證後 recovery。
7. recovery/restored retention cap。
8. explicit selector diagnostics。

延後：

9. multi-writer serialization（Web/GUI/background writer 前）。
10. attempts identity performance optimization。

### 修正後必跑 targeted regression

```text
relation edit × resolved/pending/provenance
raw sqlite helper × GC disabled × FD count
public mutation × validation/preflight/backup/export
SIGKILL × pending snapshot × commit/publish boundary
undo × corrupt newest × older valid backup
recent × same-second create/update
selector × no-match/out-of-range
```

以上通過後即可建立 stability gate，進入 Quiz core；不再執行另一輪同規模無限廣域健檢。
