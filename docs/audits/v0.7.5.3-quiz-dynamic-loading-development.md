## Scope

This checkpoint implements the remaining v0.7.5.x Quiz loading UX without changing question-generation semantics or hiding a performance regression behind a fake percentage:

- keep every curses/window operation on the main thread;
- run only the slow Quiz preparation action on one non-daemon worker thread;
- report truthful coarse stages through a thread-safe queue;
- animate the loading screen while the worker is busy;
- preserve shortage-plan reuse instead of rebuilding sources after confirmation;
- preserve worker exceptions and the existing active-session interruption recovery boundary;
- remove the controller-private `allow_shortage` parameter that had only one caller and was always false;
- retain `QuizService.start_session(... allow_shortage=...)` as a compatibility/service surface.

Out of scope: v0.7.6 search correctness, kana-only reading-question eligibility, True/False `○／×` polish, reorder feedback, history polish, and shared hanging-indent rendering.

## Progress architecture

`QuizService` now owns an observational progress context backed by `ContextVar`. It is inactive by default and therefore does not alter headless/debug callers. When the TUI worker enters `progress_reporting(reporter)`, the service emits these real stages at existing semantic boundaries:

1. `loading_sources` — immediately before source snapshot/list reads;
2. `building_questions` — immediately before `QuestionPoolBuilder.build()`;
3. `creating_session` — immediately before `QuizSessionStore.create_session()`;
4. `opening_question` — immediately before `QuizSessionStore.next_question()`.

Progress reporter failures are fail-soft and cannot change Quiz planning or persistence semantics.

The curses adapter owns the worker/thread/queue lifecycle. The main thread renders a spinner and the latest stage. The worker never calls curses. There is deliberately no cancellation boundary in this first version: if the outer loop is interrupted while preparation may be mutating Quiz persistence, the non-daemon worker is allowed to settle before the existing outer interruption hook runs.

## Persistence and thread-safety reasoning

`QuizSessionStore` is constructed before the curses loop, but its operations open fresh SQLite connections through `_connect()` rather than retaining a main-thread SQLite connection. `create_session()` already writes the session and question events in one transaction using `executemany`. Moving start preparation to the worker therefore does not reuse a Python sqlite connection across threads.

If session persistence succeeds but loading the first question subsequently fails, `QuizTuiController._load_session()` has already stored the new `session_id`. The worker exception is re-raised on the main thread; `_run_curses()` then invokes the existing `interrupt_active_session()` hook, allowing the persisted active session to become `interrupted` and recoverable instead of being left as an unexplained active session.

## Bounded dead-code cleanup

`QuizTuiController._start_session(self, *, allow_shortage: bool)` had one caller, and that caller always passed `False`. Shortage confirmation already bypasses that helper and persists the immutable pending plan through `start_planned_session(pending.plan)`.

The candidate therefore changes the private helper to `_start_session(self)` and relies on the service default `allow_shortage=False`. The service parameter itself is intentionally retained.
