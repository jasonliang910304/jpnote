# jpnote v0.7.6 Correctness / UI Development

Date: 2026-09-25 (Asia/Taipei)

Status: dev1 v2 candidate. Exact parent is post-v0.7.5.3 handoff main `975487af0900a0658f7ca233fd157396307b5cd8`.

## Dev1 A — vocabulary reading-question eligibility

The existing `vocabulary_reading_true_false()` accepted every vocabulary entry with non-empty `display` and `reading`. For kana-only entries such as `けんか` or `コーヒー`, the prompt itself therefore exposed the reading that the question was supposed to test.

The bounded correction is intentionally conservative:

- the actual vocabulary `display` used by the reading prompt must contain at least one kanji character;
- pure hiragana, katakana, long-vowel-mark, or punctuation-only displays return `None` for reading true/false and reading-trap generation;
- a kanji alias does **not** silently replace a kana-only display. Alias-based prompt selection would need a separate explicit safety policy;
- the existing long-vowel/sokuon/moraic-nasal trap algorithms are unchanged. Katakana long-vowel coverage uses a kanji prompt (`珈琲`) with katakana reading (`コーヒー`) so the trap itself remains tested without a self-revealing prompt.

This slice does not bump `GENERATOR_VERSION`: emitted question snapshot structure is unchanged; the change only removes an unsafe/self-revealing source-generator pairing.

## Dev1 B — import pre-commit prompt interruption

A real 2026-09-25 import exposed an uncaught `KeyboardInterrupt` while the user was resolving a duplicate warning. The traceback stopped at `_interactive_resolve_warnings()` -> `input()`. Code-path review confirmed that this prompt occurs before `execute_safe_mutation()`, writer-lock acquisition, the SQLite mutation transaction, Markdown refresh, and post-success source cleanup; that interrupted attempt therefore had not modified the formal database.

The UX correction is deliberately scoped to prompt boundaries that are provably pre-commit:

- duplicate-warning choice catches `EOFError` / `KeyboardInterrupt` and returns cancellation to the caller;
- safe-fix confirmation uses a tri-state pre-commit helper: yes, no, or interrupted;
- final formal-import confirmation uses the same helper;
- interruption prints a clean `已取消，未修改資料庫。` result rather than a Python traceback.

The patch intentionally does **not** add a blanket `KeyboardInterrupt` handler to `main()`. Once mutation begins, the existing transaction and `PostCommitExportError` boundary must remain authoritative: an in-transaction exception can roll back, while an interrupt after DB commit during Markdown export must continue to report that the database was already committed.

The successful post-interruption retry in the real workflow used the existing duplicate-resolution `m` path; no special migration or repair is required.

## Search analysis retained for the next slice

The `imasu` overmatch is not a one-function ranking bug. Core search has exact/whole grammar-romaji tiers followed by relaxed substring tiers, while interactive fzf filtering has its own substring path. A core-only fix would leave interactive browse behavior divergent; an fzf-only fix would do the reverse.

The next search checkpoint must therefore treat core search and fzf together and preserve useful partial search when no stronger exact/whole match exists.

## Dev2 — coupled core/fzf strong-match preference

The `imasu` issue spans two paths rather than one ranking bug:

- core search already assigns exact/whole entry matches to score tiers 0–6 and relaxed romaji/metadata substrings to later tiers;
- the fzf reload helper previously had only a folded/compact substring predicate, so a live query such as `imasu` retained `kimasu`, `shimasu`, `arimasu`, and `moraimasu` even when the intended grammar-derived `imasu` form existed.

The dev2 rule is global and query-generic rather than an `imasu` special case:

1. `entry_strong_search_terms()` defines the query-independent key/display/reading/alias/stored-romaji/normalized-romaji/grammar-derived-romaji forms corresponding to core score tiers 0–6.
2. Core repository search suppresses score 7+ candidates whenever at least one score 0–6 result exists.
3. Heterogeneous core browse makes the same decision before mistake substring records are appended.
4. fzf rows precompute a hidden normalized strong-term index once; the lightweight reload helper first detects whether any current candidate is a strong match and, if so, emits only strong rows.
5. If no strong row exists, the existing folded/compact substring behavior remains the fallback. Searches such as partial `imas` therefore continue to return useful suffix-sharing candidates.
6. Strong-index data is hidden from visible fzf rows and stripped from helper output; it is search metadata only and never becomes stored jpnote data.

This preserves the v0.7.5.2 performance architecture: romaji variants are constructed in the main process when the dataset is built, not rebuilt inside the per-keystroke helper. Query folding/compaction remains once per reload rather than once per row.

Compatibility boundary remains unchanged: no core/Quiz/public-import schema change, no migration, and no formal database mutation is required.
