## Scope and non-goals

This checkpoint closes the remaining search/fzf **performance** hot path from the v0.7.5 roadmap. It deliberately does not change search correctness or ranking semantics.

In scope:

- remove per-row Unicode/diacritic normalization from every fzf query reload;
- keep fzf helper startup isolated while avoiding irrelevant site initialization;
- avoid rebuilding the same romaji/grammar variant sets twice inside core search;
- add non-timing performance regressions and baseline/candidate output equivalence checks.

Out of scope and retained for v0.7.6:

- `imasu` substring overmatch / exact-vs-substring ranking changes;
- unifying core and interactive fzf ranking semantics;
- pure-kana reading-question eligibility, `○／×`, reorder feedback, history UI, and grammar hanging-indent fixes.

Core schema remains v5, Quiz schema remains v2, and the public import JSON schema is unchanged.

## Why fzf still uses a reload helper

fzf 0.74.3 calculates `--nth` against the line after `--with-nth` transformation; hidden original fields cannot be searched through native `--nth`. jpnote therefore keeps fzf as the selector and a small jpnote-owned reload helper as the matcher so hidden stable keys, aliases, romaji variants, meanings, sources, and mistake metadata stay searchable while only the human-facing visible column is rendered.

The optimization changes *when* normalization happens, not what matches.

## Runtime changes

### One-time fzf search index

Before this checkpoint, each query-change helper process did the following for every row:

1. reconstruct token + visible + metadata haystack;
2. NFKC/casefold the complete haystack;
3. NFKD/remove combining marks/collapse separators for the compact haystack;
4. compare the current query.

The candidate now appends two hidden columns to the temporary dataset once when the selector opens:

- folded haystack;
- compact haystack.

The helper normalizes the current query once and performs substring checks against those precomputed columns. Filtered output strips the two internal index columns before returning rows to fzf, so the row shape observed by fzf, preview placeholders, and token parsing remains unchanged.

### Lightweight helper bootstrap

`_isolated_module_command()` now uses `python -I -S -c ...` instead of `python -I -c ...`.

- `-I` continues to ignore cwd / `PYTHONPATH` shadowing.
- `-S` skips `site` / site-packages / `sitecustomize` initialization for tiny fzf helper processes.
- jpnote runtime is stdlib-only, and the helper explicitly inserts the installed application root before running the requested module.
- both search and filter-panel helper paths have isolated execution regression coverage.

### Shared lightweight text normalization

`fold_text()` and `compact_text()` moved to the stdlib-only `jpnote_app.search_text` module. `search_normalization` re-exports/uses the same functions, so matching behavior does not fork between core search and fzf helper code.

`compact_folded_text()` lets callers derive the compact form from an already-folded string instead of repeating NFKC/casefold work.

### Core search variant reuse

`entry_match_score()` already computes relaxed romaji variants and grammar-derived romaji variants before its metadata fallback. Previously `entry_search_metadata()` rebuilt those same sets again for entries that reached the fallback.

The metadata builder now accepts optional precomputed variant sets. Its old one-argument behavior is preserved for browse/fzf callers.

## Baseline/candidate equivalence

Dataset: historical 1019-item schema-v5 snapshot used by prior performance gates. All-type browse catalog contains 1046 rows after mistakes are included.

Exact fzf output was compared line-for-line between v0.7.5.1 and the candidate for:

- empty query;
- `k`, `ka`;
- `kiseki`, `ki se ki`;
- `ninaru`, `imasu`, `kyoushitsu`;
- Japanese query `理由`;
- level `N3`;
- `wrong`, `未分類`;
- no-match query `zzzzzz`.

All outputs are byte-identical after the candidate strips its internal index columns.

Core `search_entries()` output was serialized with stable key ordering and compared for Japanese, kana, spaced/compact romaji, grammar romaji, level, metadata, wildcard-like text, and no-match queries. Result content and ranking are identical.

## Performance evidence

To avoid overstating a container-specific Python `sitecustomize` penalty, the fzf subprocess comparison forces `-S` on **both** baseline and candidate. Seven runs were collected per representative query; values below are medians.

| Query | v0.7.5.1 helper | v0.7.5.2 candidate |
| --- | ---: | ---: |
| `k` | 68.2 ms | 26.1 ms |
| `ka` | 90.3 ms | 25.8 ms |
| `kanji` | 100.0 ms | 27.2 ms |
| `ninaru` | 99.8 ms | 27.0 ms |
| `理由` | 100.5 ms | 28.3 ms |
| `N3` | 58.4 ms | 29.9 ms |
| `wrong` | 100.8 ms | 27.1 ms |

Candidate one-time index construction inside the already-running process is approximately 48 ms for the 1046-row dataset. This intentionally trades a bounded selector-open cost for much cheaper repeated keypress reloads. The index stays in the temporary dataset only; fzf itself continues receiving raw rows without the extra columns.

Core search median examples on the same 1019-item snapshot:

| Query | v0.7.5.1 | candidate | matches |
| --- | ---: | ---: | ---: |
| `kiseki` | 159.6 ms | 137.2 ms | 2 |

| `N3` | 105.2 ms | 95.9 ms | 847 |

These are development-container measurements, not a claim about exact latency on the user's Arch machine. The release gate should focus on behavior and real-fzf functionality; the user can judge interactive smoothness after installation.

## Regression guards

New/updated tests cover:

- indexed dataset matching equals the legacy per-row normalization algorithm;
- filtered helper output restores the exact raw row shape;
- indexed reload normalizes the query O(1), not once per dataset row;
- compacting an already-folded value is exactly equivalent to `compact_text(original)`;
- core search metadata fall-through reuses precomputed variant sets;
- search helper still ignores cwd / `PYTHONPATH` shadowing;
- filter-panel helper runs correctly with `-I -S`;
- existing mocked-fzf contracts remain `--disabled` + reload-based;
- real-fzf integration remains a required actual-Arch gate because the assistant container has no `fzf` binary.

Final version-bumped segmented repository gate covers all 513 collected tests as `512 passed, 1 skipped, 36 subtests passed`; the only skip is the assistant container's missing real-fzf binary. App-only coverage is `78%` (9398 statements / 2070 missed). Isolated 0.7.5.2 install + reinstall, version/help/Quiz-help smoke, compileall, and `git diff --check` all pass before artifact delivery.

## Newly confirmed v0.7.6 Quiz backlog

User screenshot/real usage exposed a separate question-quality issue: a vocabulary item whose prompt is already kana-only can still generate a reading True/False question, e.g. `けんか` → asking whether its reading is `けんか`. This has no information gain.

Planned v0.7.6 guard:

- display/canonical containing only hiragana/katakana/long-vowel mark/punctuation does not generate a reading question;
- this applies to both hiragana and katakana, not just the screenshot case;
- a kanji alias must not silently replace a kana canonical prompt unless a separate explicit/safe prompt-selection rule is designed;
- this is distinct from the existing homophone guard: homophone safety prevents multiple valid answers, while this guard prevents a self-revealing question type.

The user also reported that Quiz startup is noticeably faster after v0.7.5/v0.7.5.1. Future dynamic-loading work must preserve that real-world performance baseline rather than hiding a regression behind a spinner.
